# TAD v4.0.10

Installer data-safety hotfix. Framework writes during install, upgrade and migrate are now atomic, rollback actually restores and verifies what it claims to restore, and version stamps land last — closing the two defects behind the 2026-11-01 fleet damage, where a mid-write failure truncated files to zero bytes and the rollback that followed restored nothing (`restored: [none]`) while leaving a mixed version face behind.

## What changed

- **Atomic writes.** Every framework write in the mutation phase goes through a stage-verify-rename helper: the new content is written to a staging file in the same directory, byte-compared against its source, and only then renamed into place. A failed write can no longer truncate the file already there. The three project-knowledge seed copies are converted as well, and the install branch gained the create-only guard its upgrade and migrate siblings already had, so a project-owned README is never overwritten.
- **Rollback that restores.** Rollback no longer stops at its first failure: every preserved file is restored from the pre-run snapshot and byte-verified, and the run ends with an explicit `ROLLBACK-RESULT` line — full, partial or none, with restored and failed counts computed from the same entry list as the per-file coverage lines. When the result is not full, a MANUAL-RECOVERY block names the durable backup and the snapshot path and lists the failed entries, instead of implying a recovery that did not happen.
- **Version stamps last.** The version faces are stamped only after every written face verifies, through the same atomic helper; any write failure stops the run at the first failure point. A failed install can no longer leave the version face ahead of the tree it describes.
- **Fault-injection regression.** The installer data-safety fixture gains cases aw.1–aw.4 plus aw.2b: a single-point sync failure, a rollback that itself hits a restore failure, a first-entry rollback failure, a clean-upgrade control, and a stamp-point failure. Fault injection is scoped to paths inside the target tree and each case carries phase witnesses, so an assertion cannot pass vacuously on a backup-phase copy. Publish-protocol step3f gains the installer-atomic transcript surface these cases feed; all five cases pass on this release's candidate tree (`installer-atomic-20261101.md`).
- **One compatibility guard.** Pack-meta generation now skips — with a named log line — a target skill directory that has no source counterpart, instead of aborting the install. Before this change the same situation was silently swallowed and produced a header-only meta file; skipping is logged, never silent, and a failure on a directory that does exist still aborts.

Verification: the hotfix chain ran the full gate sequence — Gate 2 dual review with a revision round, Gate 3 dual review PASS (P0/P1 = 0 on both faces, all fourteen acceptance rows independently recomputed), Gate 4 CONDITIONAL PASS with three real runs on a copy of a real 4.0.8 project: an injected sync failure left the tree byte-identical with the version face unmoved, an added rollback-time failure was accounted exactly (partial result, failed entry named, recovery paths verified on disk), and a clean upgrade reconciled the framework face (898 forward / 588 reverse files) with zero mismatch. The legacy test suite was additionally re-run on a git tree to close the one acceptance row the sync folder cannot execute.
