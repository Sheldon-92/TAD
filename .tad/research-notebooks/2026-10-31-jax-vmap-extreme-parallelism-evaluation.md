## 0. 结论先行

- **对「现在就全量移植 TCG 环境到 JAX」：NO-GO。** 主因不是机制不成立，而是（a）现行基线的真实吞吐与时间构成从未测过——先测基线再谈优化（principles: Measure Before Optimizing）；（b）移植的真实成本不在 vmap 机制，而在卡牌效果的长尾（见 §2.2），在基线未测、卡池未定前无法估。
- **对「有界 spike」：CONDITIONAL GO。** 成立条件与止损线见 §5。机制面已被本机代理测量证实成立（§1）：把 Python 逐局循环换成编译后的批量 rollout，在本机 CPU 上就是约 50–360× 量级的机制差距——现行自对弈生成器若确为 Python 逐局步进（IDEA 转述，未验），其瓶颈形状与代理测量的 A 配置同型。（更正注记，2026-10-31：本句倍数原表述为「100–500× 量级」，经独立评审 P2 指出与 §1 自家数据不符——按 §1 同配置 C/A 比值重算实为 49.7×（batch=1）至 358.5×（batch=512），已更正为「约 50–360×」；§1 数据与本报告结论未动。）
- **Jaxpot 的「1 亿步/秒」不许搬运到 TCG**（理由 §3.2）。

## 1. 本机实测：机制开销代理测量（CPU，非 TCG、非 GPU）

方法：通用微型 env-step 代理（解析式 gridworld：状态 = 位置/速度/能量/步数/RNG key；一步含 8→16→4 的小型策略网络前向 + 终止自动重置）。三种执行形态在同一代理函数、同一台 VM（4 CPU、7 GB RAM、jax 0.12.0.1 CPU wheel）上对比；每点 200 步 rollout、3 次取最快。原始输出：证据目录 `bench-output.txt`（`recomputed`，命令与脚本同目录留档）。

| 形态 | batch=1 | 8 | 64 | 512 | 4096 | 16384 |
|---|---|---|---|---|---|---|
| A. NumPy Python 逐个循环 | 45,003 | 43,347 | 25,511 | 27,181 | 未跑（太慢） | 未跑 |
| B. jitted 单步、Python 逐个调用 | 41,471 | 27,415 | 19,892 | 17,562 | 未跑（太慢） | 未跑 |
| C. jit+vmap+lax.scan 整段编译 | 2,237,787 | 2,629,831 | 6,709,918 | 9,744,086 | 4,979,083 | 8,833,363 |

（单位：env-steps/s。C 在 4 核 CPU 上约 batch 512 起饱和在 5M–10M 区间，曲线非单调属测量噪声与线程争用范围。）

**读数规则（只许这样读）：**
1. A≈B 且都平坦 → 在 Python 逐局步进形态下，吞吐被**解释器/调度开销**锁死（本代理约 2.5万–4.5万步/秒），把单步换成 jit 版本救不了（B 甚至略差，多了 dispatch 成本）。这正是「自对弈生成器是 Python 循环」时的瓶颈形状。
2. C 的量级跃升来自**把循环搬进编译产物**（vmap 批量 + scan 串步，Python 退出内环），与 Jaxpot 模式的机制主张一致。此数字只证明机制在本机成立，**不代表任何真实环境的吞吐**——代理 step 远比真实 TCG step 便宜。
3. **填充税实测（D 配置）**：每个 env 的真实子步数在 1–8 间随机（均值 4.5），vmap 必须按 8 槽全算再掩码。掩码浪费率 0.44 时，槽位吞吐与 C 同量级，但**有效吞吐 ≈ 槽位吞吐 × 0.56**——填充税与浪费率线性。这是 §2.1/§2.4 的定量锚点：变长结构在 vmap 下不是不能做，而是按填充比例交税。

## 2. IDEA 评估问题一：Pokémon TCG 环境能否 JAX 重写

vmap/jit 的硬前提：**静态形状、无数据依赖的 Python 控制流、纯函数、显式 RNG**。逐项对照 TCG：

### 2.1 不定长手牌/区域 — 可解，且 TCG 有先天上限
- 手牌、弃牌堆张数可变，但 Pokémon TCG 的全部区域都被 60 张牌库封顶：牌库恰 60、手牌 ≤60、奖赏卡 6、后备区 ≤5、弃牌 ≤60。于是每个区域都可编码为**定长 card-id 数组 + 有效长度/掩码**，形状静态成立。这是比开放域环境（如文本游戏）好得多的处境。
- 代价即 §1 的填充税：按最坏情况定长，平均占用越低税越重。手牌均值远低于 60 时，可按区域分别定长（手牌槽 < 牌库槽）压税，但税不归零。

### 2.2 效果链与触发时序 — 真正的成本所在
- 卡牌效果 = 数据依赖分支 + 优先窗口 + 可选（"may"）抉择 + 替代效果 + 触发队列。在 JAX 里只能落成：**定深的效果结算循环 + 掩码槽位**，每个效果实现为按 card-id 索引的纯函数（gather/switch 查效果表）。
- 机制上可行，但工程量由**效果长尾**决定：目标卡池里每张有独特效果的卡都要一份纯函数实现 + 对照测试。新系列发售 = 持续新增。这是人月级且持续复发的成本，是本评估认定移植代价的主项——不在 vmap，在效果表。

### 2.3 不完全信息 — 机制无碍，算法另算
- 完整状态（含对方手牌、牌库序）在 JAX 侧照常持有；观测 = 对完整状态做掩码的视图函数；确定化采样可由 PRNG key 分裂完成。Jaxpot 支持 imperfect-information games（Dark Hex）说明框架层有先例（`reported`，来源件转述，未独立核）。
- 真正的难点是算法层（信念状态、信息集搜索），与 vmap 机制正交，不因换 JAX 而消失或新增。

### 2.4 可变长回合与对局 — 标准手法可解
- 回合内动作数可变 → 按**单个动作**步进（出牌/攻击/结束回合都是一个 step）+ done 掩码 + 自动重置，可变回合长度自然消解；本报告代理 step 的终止自动重置即其微缩版。残余变长只剩对局总长差异，落在批量维度的填充税里（§1 D 配置口径）。

### 2.5 随机性 — 无碍
- 洗牌 = 对定长 60 数组的排列，`jax.random.permutation` 可 vmap；全部随机源走显式 key 分裂，与纯函数前提兼容。

### 2.6 小结
**能重写，没有机制级死刑项；成本结构 = 效果长尾实现 + 与 Python 原环境的差分测试。** 差分测试（同种子同轨迹对照）是正确性前提，而它要求原环境代码在场——见未验清单。

## 3. IDEA 评估问题二：Jaxpot 模式可迁移性

### 3.1 可迁移
- **env-as-pure-function + vmap + scan 整段 rollout 编译**：本机代理测量已证机制成立且量级显著（§1）。现行生成器若为 Python 逐局步进，迁移收益的大头在这里，与卡种无关。
- **PPO / league play 的训练侧结构**：与环境实现解耦，可随 JAX 环境一并采用（`reported`，依来源件对 Jaxpot 的描述）。
- **不完全信息博弈的框架先例**（Dark Hex，`reported`）。

### 3.2 不可迁移 / 不是免费的
- **「1 亿步/秒」这个数字**：是 Jaxpot 对其棋类环境在 GPU 上的主张（`reported`）。棋类 step 小而均匀；TCG step 的状态量（多区域 × 60 槽编码）与分支量高出几个量级，单步成本、批量上限都会差几个数量级。把该数字写进 TCG 的任何预期都是伪造外推。
- **对现行 Python 环境的加速**：不存在桥。Jaxpot 的环境是 JAX 原生从头写的；收益只在**全量重写**后出现，过渡期双份维护。
- **GPU 批量上限**：batch × 单状态字节数决定显存占用；TCG 状态远大于棋类，批量天花板大概率显存-bound。具体数需真实状态尺寸才能算——本机无从测起（未验清单）。

### 3.3 IDEA 附带问题：vmap 用于 agent evaluation？
- 若 eval 的 step 是**外部 LLM API 调用**（延迟-bound、非数组运算），vmap 不适用——批量并行靠异步请求层，不靠 JAX。
- 若 eval 是**本地模型的批量打分**（如本地 judge 模型对数千 prompt 变体推理），vmap/批量推理模式成立，但那是推理引擎的批处理问题，与 Jaxpot 的环境并行是两回事。结论：对 TAD 现行以 API agent 为主的 eval 面，**不构成可迁移收益**。

## 4. IDEA 评估问题三：Hydra config 模式对 TAD capability pack 的启示

- Hydra 的可迁移内核是 **configuration over code**：换模型/loss/环境只改配置、不动训练循环。
- 对应到 TAD：pack 本体是判断文本（judgment），不是参数化模块，**类比在 pack 内容层不成立**；成立的是**评测与选择层**——pack 的 eval（fixtures、runner、判分口径）目前若靠改脚本切换 pack/题集，应改为配置驱动（pack 名 + fixture 集 + 阈值进配置，runner 不动）。这与本机实测的机制教训同向：把可变部分赶进数据/配置，把循环（评测管线）固定成一份已验证的实现。
- 量级判断：这是小改良，不是架构事件；值得在下次动 pack-eval 管线时顺手做，不值得单独立项。

## 5. go/no-go 与成立条件

**裁定：全量移植 NO-GO（现在）；有界 spike CONDITIONAL GO。**

spike 的成立条件（四项全备才开工）：
1. **基线在场**：`self_play.py` / `selfplay_gen.py` 及其运行环境到位，先测出基线吞吐与时间构成（env step 占比 vs 策略推理占比）。若时间大头在策略推理而非 env step，JAX 化 env 的收益上限先被这个比例封顶，spike 目标随之改写。
2. **GPU 机器一台**（消费级即可）：CPU 代理数字不外推 GPU；spike 的判定数字必须在目标形态硬件上测。
3. **spike 射程钉死**：最小 TCG 内核——60 张定长编码、约 20 张卡的效果、一对固定牌组、自对弈 rollout；与 Python 原环境做同种子差分对照（轨迹级）。
4. **止损线先行**：spike 卡池上端到端吞吐（env+推理合计）未达基线 **10×** 则停，不扩卡池、不进全量移植讨论（阈值取 principles 的 spike pivot 精神，具体倍数由 spike 立项时复核）。

全量移植的 go 条件（spike 之后再议）：spike 过线 + 目标卡池的效果覆盖清单与估算 + 新系列效果的持续维护归属有人。
