## 2. 2026-09-14 后停滞成因一查

已查面清单：

- 写入路径：`.tad/hooks/post-write-sync.sh` 的 `_trace_file_today()` 写 `.tad/evidence/traces/<YYYY-MM-DD>.jsonl`，路径为 cwd 相对；脚本在册未删。
- 触发接线（现行）：`.codex/hooks.json` PostToolUse 以 matcher `^apply_patch$` 挂 post-write-sync.sh 在册；tad.sh 生成模板同款在册；Cursor 侧有 `.tad/hooks/lib/cursor-post-write.sh` 转码垫片指向同一脚本。即「接线在、写手在」，缺的是触发。
- 通道面：traces 末件 2026-09-14；此后本仓的实际工作通道以 Muse 原生 subagent 等非 Codex harness 通道为主——该通道不读 `.codex/hooks.json`、不触发 Codex PostToolUse；Claude Code 平台路径已于 v3.0.0 移除（其 hooks 接线不在仓内现行面）。

结论：停滞与「捕获面单一挂靠特定 harness 的 hooks、而工作通道已迁移」一致——正是捕获设计自陈的已知限制（触发稳定性依赖 harness hooks）。**精确断点成因记「未定」**：2026-09-14 当周的通道切换时点、hook trust 状态、Codex 侧 apply_patch 工具命名变化等因素未逐一证伪，不冒充已定论。后续捕获实施票若立项，第一步应为多触发面（不依赖单一 harness）设计，而非先复活旧面。

## 3. 三级上限校准意见（只许收紧不许放宽超 2 倍的约束内）

**意见：三值维持设计值**——单事件 ≤8 KB、单日 ≤5 MB、总量 ≤100 MB。依据：

- 旧面实测单行最大 849 B、p95 313 B；新捕获面（原始工具观察，含工具入参与输出）的事件体量预期显著大于旧面（工件解析事件）。8 KB 约为旧面最大值的 9.4 倍：有余量、又能挡住失控事件，收紧（如降到 2 KB）会误伤新面的正常大事件且无实测支持。
- 5 MB/日约为旧面日均（9.3 KB）的 500 倍以上：对正常工作不构成约束、纯熔断口径，无收紧必要。
- 100 MB 总量按 5 MB/日熔断计约 20 天满仓，须与设计的轮转/归档策略配套（由捕获实施票定义）；总量值本身维持。
- 复校触发：捕获试点首周实测数据到手后，按新面单事件 p95 与日量实测复校三值一次；复校只许在「维持或收紧」方向动，放宽须 PM 裁（设计约束）。
