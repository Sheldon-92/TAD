## 选项

1. **案一 恢复分支同步** — 把两树重新定期/收口触发提交到 maintainer-evidence 分支，恢复 F-18 原设计载体，并加新鲜度看守。
2. **案二 主仓例外清单常态化** — 维护一份例外登记册，册内关键证据件逐件 `git add -f` 入主仓；册外件不设 git 载体（维持磁盘＋Syncthing 现状）。
3. **案三 分级混合载体** — 关键件走案二入主仓、批量过程件走案一入分支，一份登记册统管两路与分级判据。

## 案一 恢复分支同步

### 机制描述
链收口（或定期）触发一次脚本化同步：以显式清单把 `.tad/evidence/`、`.tad/archive/` 两树当前状态提交到 maintainer-evidence 分支并推送 origin；两树在主仓维持 `.gitignore` 整树忽略不变。防再停摆的看守与同步同批落地：定期（如 PM 周期 review 时）复跑 S1 summary 已留的复跑命令序列，重算四锚——no-carrier 锚值回升超阈值或分支尖年龄超期即报警。新证据「自动有载体」的保证来自收口动作清单中的固定同步步＋看守的事后可测性，不来自任何人的记忆。

### 一次性成本
- 重建同步流程/脚本：仓内现无任何现存同步脚本可直接复用（本步实查 `.tad/hooks/`、`.tad/scripts/`、`tad.sh` 三处均无 maintainer-evidence 引用），2026-09-06 的同步是手工 chore 提交，流程须从零写并验。
- 首轮全量补同步：8,706 件 no-carrier（46,878,109 B，约 44.7 MiB 新内容）＋5 件 stale-content 内容更新入分支。
- 写死防呆：两树被 gitignore，朴素 `git add` 会静默一件不加——脚本必须用显式清单/`-f`，且同步后以四锚复算断言收尾（no-carrier 应降至约 0，只剩同步时点后新增件），不许绿着空转。

### 常态运维负担
每链收口多一个脚本化动作（分钟级）；每次 PM 周期 review 多一次四锚复算（命令现成，S1 summary 已留全序列）。分支体积随证据积累单调增长——这是其设计用途（可追溯），无清理义务。单人运维可承受。

### 风险与失效模式
- **静默再停摆（已被实证的失效模式）**：分支尖停于 2026-09-06 后约四周无人察觉，直到 R1 自查才发现——本案若只恢复同步、不落看守，复发概率高；看守把「发现停摆」从偶然自查变成定期机械复算，失效模式由静默变显性。
- 同步脚本假绿：gitignore 致空提交而脚本报成功——靠同步后四锚断言堵（见一次性成本）。
- 分支膨胀失控：影响面中 yolo 一类批量件占比极高（见盘上证据），分支会持续变大；但分支不进发行面，膨胀只影响 clone/检出该分支的维护动作，不影响 F-18 的发行体积目标。

### 与 F-18 发行瘦身意图的相容性
**完全相容——本案即 F-18 原设计。** F-18 原文（AUDIT-20260816「发行重量」节）定的问题是发行路径下载整棵工作树 30.19 MB、实际只需 4.54 MB；其有利条件是 evidence 已在 TAD_ZERO_TOUCH、运行时不读已提交 evidence、tad.sh 拉 tarball 快照故移出 main 即刻生效。EPIC-20260816 Phase 4 的 Scope 原文即「将两树移出 main 分支工作树（保留于 orphan 分支以维持可追溯），不做 git 历史重写」，SC3 主判据为两树在 main 的 `git ls-files` 计数为 0。本案不碰 main 的发行面、不要求修订任何判据。已知可接受副作用（查旧证据需 `git show`/worktree 看 orphan 分支）是 Epic 当时已明示接受的。

### 盘上证据
- 分支仍活：尖 `8713ea4e`（2026-09-06），本地与 origin 远端跟踪引用同尖（本步 rev-parse 实查）；分支尖提交信息为 “sync 134 post-phase4 evidence and archive records”，与日期桶分布互证同步是批量动作（2026-08-26/27/29 三桶合计 2,998 件，其后锐减）。
- 分支存量有效：carried 4,355 件与盘上逐字节相同、stale 仅 5 件——分支不是废墟，恢复同步是续接而非重建。
- branch-only 16 件只存在于分支（盘上无副本）：本案天然保全这 16 件的唯一载体；弃分支路线必须先单独处置它们。

## 案二 主仓例外清单常态化

### 机制描述
维护一份例外登记册：被判定为「关键证据」的件逐件 `git add -f` 入主仓并登记在册；册外件不进任何 git 载体，继续靠工作区磁盘＋Syncthing 多端副本存续。新证据的载体保证是「关键件在收口时被登记」这一人工判读动作；非关键件按设计即无 git 载体。

### 一次性成本
- 建登记册＋「关键」判据；存量甄别：以 S1 分类计数表按目录估算，关键目录（reviews 256、designs 20、completions 4、pm 101、gate4 1、activation-packages 5、decisions 1）no-carrier 合计约 388 件、约 1.96 MB，逐件甄别入册的工作量远小于全量，但判据边界件需逐件裁。
- **覆盖缺口是设计内的**：8,706 件 no-carrier 中约 8,300 件（yolo 7,737 件/40,078,026 B、experiments 131 件、acceptance-tests 254 件等批量过程件）按本案设计不入册，即维持无 git 载体现状——本案只解决「关键少数」的载体，不解决影响面全体。

### 常态运维负担
每件关键证据收口时多一步登记＋`-f` 入仓；登记册须定期与 main 实际 tracked 面对账（漂移审计）。单件负担小，但判读动作不可脚本化（「这件关不关键」是判断，不是机械匹配）。

### 风险与失效模式
- **例外蔓延（已有轨迹）**：R1 第一批链已以单批例外把交付物 `-f` 入主仓，主仓两树 tracked 现为 3 件——SC3 的「0」在实践中已被突破；常态化后每条链都有动机把自己的件说成关键，主仓体积按 F-18 当年要治的病因（整树 65.49 MB 量级）反向回涨，只是速度慢。
- 登记册与实际 tracked 面漂移：登记了没入仓、入仓了没登记，两向都会发生，无机械看守即静默。
- 非关键件载体真空长期化：批量过程件在磁盘副本全失时无任何版本化载体可回——本案接受此风险但不消除它。

### 与 F-18 发行瘦身意图的相容性
**部分相容，且须以显式修订 F-18 判据为前提来认。** 与 SC3 主判据（两树 main `git ls-files`＝0）字面冲突：每一件例外都直接进入发行 tarball。体积上，关键少数约 1.96 MB 相对瘦身后 8.70 MB 的 tarball（EPIC 达成值）占比可控；但 F-18 的意图不只是体积数字，还包括「发行面不带维护者证据」这条边界本身。采纳本案等于把该边界从「零」改为「受治理的少数」——是 Epic 级判据修订，须由 PM/人显式拍板并给登记册设总量上限，否则相容性随蔓延逐年失效。

### 盘上证据
- 先例在盘：R1 链 Gate 2 合并裁定「三件交付物逐件 `git add -f` 单文件例外入主仓」；本步实查主仓两树 tracked 恰 3 件（`.tad/evidence/pm/downstream-versions.md`、`.tad/evidence/reviews/2026-09-15-gate4-acceptance-platform-adapters.md`、`.tad/archive/next/NEXT-completed-through-20261004.md`）。
- 关键少数规模可估：见一次性成本的目录合计（引 S1 分类计数表）。

## 案三 分级混合载体

### 机制描述
一份登记册统管两路：关键件（判据拟定为 Gate verdict、设计件、COMPLETION、PM 裁定/台账类——即后续链会当权威引用的件）走案二入主仓；批量过程件走案一入 maintainer-evidence 分支；登记册给每类路径记默认分级，新目录出现时补判据。新证据的载体保证 = 分级判据的目录级默认（大部分件按所在目录自动定路）＋收口登记动作。

### 一次性成本
案一与案二成本的并集减去重叠：同步脚本与看守仍须全建（批量件占影响面 88.9% 的件数，不建分支路等于没解决主体）；登记册与关键件甄别同案二（约 388 件）；外加分级判据本身的设计与首轮全目录定级（可按目录默认整表给出，逐件甄别只发生在边界目录）。

### 常态运维负担
三案中最高：同步动作＋登记动作＋分级判据维护＋两路各自的对账（分支新鲜度、登记册 vs tracked 面）。单人 CLI 运维下，每多一套机制就多一个静默失效点。

### 风险与失效模式
- **两路缝隙**：新目录未定级、边界件判错路——件可能两路都以为对方管而双双漏掉；案一单路没有这种缝隙。
- 判据边界争议：同一件被不同链判成不同级，登记册口径漂移。
- 继承案二的蔓延风险（主仓路）与案一的停摆风险（分支路，靠看守缓解）——两个失效面都要防，防线也是两套。

### 与 F-18 发行瘦身意图的相容性
**部分相容**：分支路完全相容（同案一）；主仓路同案二，与 SC3 字面判据冲突，但受分级判据与关键少数规模（约 388 件/约 1.96 MB）约束，体积影响有界。同样须显式修订 F-18 判据才成立。

### 盘上证据
- 影响面天然双峰，分级有据：no-carrier 中 yolo 一类目录独占 7,737 件（88.9%）、40,078,026 B（85.5%），是批量过程件主体；关键目录合计仅约 388 件、约 1.96 MB。分布本身支持「少数关键＋多数批量」的分法——这是案三最有力的事实基础。
- 反面证据：本仓刚因「机制件多、装载面缺失」吃过合规失败（装载层问题），再叠一套双路＋判据的机制，与「先简单、能跑再说」的现状方向相悖。

## 迁移输入形态（Q4）

选定案落地时，S1 产物转后续恢复执行链输入的形态（只定形态，本链不执行）：

- **主输入**：`inventory-manifest.jsonl`（13,082 行，逐件 path/tree/class/bytes/date_bucket）即执行链的工作清单，按 class 分三队：① `no-carrier` 8,706 行＋`stale-content` 5 行 = 待入载体队列（案一全量入分支；案二/案三先按登记册/分级过滤）；② `branch-only` 16 行 = 对账例外队（盘上无副本，执行链须逐件确认保留或明示弃置，不许默认吞掉）；③ `carried` 4,355 行 = 免动队，仅作执行后复算的基线。
- **执行前新鲜度**：manifest 是 as_of 2026-10-04T22:16Z 的快照；执行链开跑前先按 S1 summary 的复跑命令序列重算四锚，新旧差额（执行时点后新增件）以新增行追加进清单，不改首跑锚值口径。

- **案二/案三附加列**：登记册即 manifest 的过滤视图＋tier 列（main / branch / none），由 PM 在执行链设计时按目录默认＋边界逐件定级生成。

## 推荐

**推荐案一（恢复分支同步＋脚本化＋新鲜度看守）。**

推荐依据：
1. **相容性零代价**：案一即 F-18/EPIC-20260816 Phase 4 的原设计，不修订任何 Epic 判据；案二、案三都须先显式修订 SC3 才能成立，为「便利」改「边界」不划算。
2. **覆盖完整**：案一一次覆盖 8,706＋5 件全部影响面，并保全 branch-only 16 件的唯一载体；案二按设计留下约 8,300 件无 git 载体；案三覆盖完整但靠两套机制。
3. **失效模式已知且可防**：案一的历史失效只有一例且形态明确（静默停摆），看守（四锚定期复算，命令现成）正对着它；案二的蔓延与案三的缝隙是持续性、渐进性失效，更难设阈值报警。
4. **运维最轻**：单人维护的仓，一套机制一套看守；本仓 principles 亦有「单人 CLI 环境优先简单软机制」的既定判断。
5. 案二的便利并非全失：真有个别件需在主仓直读时，R1 先例的单批 `-f` 例外仍可逐次裁定使用——不必为偶发便利建常设登记册。

**置信度：中高。** 事实面（影响面构成、分支状态、F-18 原文、无现存脚本）全部盘上实测/原件直读，无估计混入；判断面（便利 vs 边界的取舍）依赖「关键件跨链直读需求不频繁」这一前提，该前提目前无使用数据可证（见未知项 1），若未来 usage log 攒出高频直读证据，此推荐应重议。
