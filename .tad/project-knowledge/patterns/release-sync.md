### A Mirror/Parity `--fix` That Copies a Tree Wholesale Destroys the Source's Gitignore Semantics - 2026-07-12
- **Discovery**: `release-verify.sh parity --fix` rsyncs `.claude/skills` → `.agents/skills` wholesale. `.claude/skills/local/` is gitignored by contract (save-skill: local-only, never distributed), but the mirror copied it to `.agents/skills/local/`, where NO ignore rule existed — local-only content became git-visible in a PUBLIC repo. On 2026-07-12 only harmless scaffolds (`_example.md`/`_index.md`) leaked, but any real local skill would have been one `git add -A` from publication. Ignore rules are PATH-specific: they do not travel with mirrored content. Mitigation applied (rm + `.agents/skills/local/` added to .gitignore); ROOT FIX STILL OPEN — parity tool must exclude `local/` (needs an Alex bugfix handoff).
- **Action**: For every mirror/sync/parity tool, make the exclusion set include the source side's ignored-by-contract subtrees (e.g., rsync `--exclude local/`), AND add matching ignore rules on the destination side as defense-in-depth. Whenever a "never distribute" contract is attached to a path, sweep every mirror/copy loop that touches its parent tree — the same every-granularity discipline as the L1 deny-list principles (2026-06-01), extended to ignore semantics.
- **failure_mode**: Naive default: trust that gitignored content stays private because the source path is ignored, then mirror the parent tree wholesale. Why wrong: gitignore semantics are path-specific — the mirrored copy at the destination has no ignore rule, so private-by-contract content silently becomes trackable/publishable in the destination tree, converting an isolation contract into a publication vector.
- **Grounded in**: .tad/evidence/journal/memory-redirect-capture-layer-2026-07-12.md finding 1, .tad/hooks/lib/release-verify.sh (parity), .gitignore (`.agents/skills/local/` entry)
- **AMENDED 2026-08-06 — the "ROOT FIX STILL OPEN" note is obsolete; both layers are now closed**:
  verified in place on 2026-08-06 — `.gitignore:16` ignores `.agents/skills/local/` (destination-side
  defense), and `.tad/hooks/lib/release-verify.sh:681` now runs
  `rsync -a --delete --exclude=/local/ …` (tool-side exclusion). **The git-visibility hazard this
  entry describes is closed.** What remains is narrower and must be stated separately: a *bare*
  `rsync` (not via the parity tool) still materializes private `local/` content into the working
  tree of a public repo — invisible to `git status` precisely because of the ignore rule that fixes
  the other half. A guard against whole-tree copying must therefore test the **filesystem**
  (`diff -rq`, `test ! -e`), never `git status`.
  ⚠️ **Why this amendment matters beyond the fact**: on 2026-08-06 a contract cited this entry's
  headline to justify a guard, missed the mitigation clause, and consequently built an AC against
  the already-fixed hazard — one with zero discriminative power against the live residual risk.
  See `ac-verification.md` §`Before Trusting a Guard, Measure Whether Its Trigger Condition Can
  Even Occur`. Read cited entries to the end.

### Identity Early-Exits Blind Downstream Checks: Content Guards Must Run Before Byte-Parity Short-Circuits and Match All Serialization Forms - 2026-08-03
- **Context**: codex-wiring-stopbleed. `release-verify.sh parity` exited 0 as soon as `.claude/skills` and `.agents/skills` were byte-identical — but "byte-identical" includes "identically broken": 36 platform-coupled `reference: ".claude/skills/…"` lines survived a month inside a green parity gate because both trees carried the same bad content. A naive mutation probe (inject bad line into one tree) proved nothing: it broke byte-identity, so the pre-existing diff check FAILed and masked whether the new content guard even ran. Second layer: the guard initially matched only double-quoted `reference: "…"` values; single-quoted and bare YAML forms would have passed.
- **Discovery**: (1) A byte-parity early-exit makes every check placed after it unreachable in the steady state the repo actually lives in (trees synced). Content-level guards must run unconditionally BEFORE the identity short-circuit; in `--fix` mode they must run on the post-rsync final state or they deadlock against the rsync that would fix the tree. (2) The only mutation probe that isolates a content guard from an identity check is a dual-tree injection that PRESERVES byte-identity, asserted via the guard's dedicated failure-message text — plus a single-tree injection as regression proof the identity check still works. (3) A declaration matcher is an allow-list over serialization syntax: it must cover every legal form (double-quoted/single-quoted/bare) or the uncovered form becomes the bypass.
- **Action**: When adding a content guard to a verifier that has an equality/identity early-exit: place the guard before the early-exit; define fix-mode ordering explicitly; prove it with a byte-identity-preserving dual-site mutation asserting the guard's own message; enumerate all serialization forms the guarded declaration can legally take.
- **failure_mode**: Naive default: append the new check after the existing logic and probe it by mutating one side. Why wrong: the early-exit returns before the check in the synced steady state (guard is dead code exactly when needed), and the one-sided probe trips the identity diff — a green "probe" that never exercised the guard.
- **Grounded in**: .tad/hooks/lib/release-verify.sh parity (guard at L552 pre-early-exit), .tad/evidence/acceptance-tests/codex-wiring-stopbleed/AC-06-parity-injection.sh (quote-agnostic dual-tree probe), .tad/archive/handoffs/HANDOFF-20260803-codex-wiring-stopbleed.md §3.2.5 + Audit Trail

### A Self-Updating Installer That Decides "Already Latest" Before Fetching Cannot Ship Its Own Repair — the Fix Is Unreachable on Exactly the Machines That Need It - 2026-08-11

- **Context**: F8, the first smoke test of TAD v2.41.0's install paths, run because publish-only had shipped a release whose entire premise was "downstream pulls it themselves" — and nobody had ever pulled it. Both fresh-install paths passed. The upgrade variant using the fixture's own `tad.sh` failed: a 2.30.0 project running its local installer printed `Nothing to do. TAD v2.30.0 is already installed.` and exited 0. Mechanism, read off the 2.30.0 source: `STATE=$(detect_state)` at L961 runs **before** the download at L1073 and before `derive_target_version` at L1079, so at decision time `TARGET_VERSION` is still the literal `"2.30.0"` baked in at L22 — identical to the local `.tad/version.txt` — hence `current`, hence the state gate exits. v2.41.0 fixes exactly this by calling `probe_remote_version` before `detect_state` and forcing `ACTION=upgrade` when the probe fails, refusing to claim "latest" against an unverified target. Scope, measured: `git tag --contains ac0699f` returns only `v2.41.0`, and `git show v2.40.0:tad.sh | grep -c probe_remote_version` returns 0 — every version from 2.30.0 through 2.40.x carries the defect, covering 25 live downstream projects.
- **Discovery**: When the upgrade decision is computed from a constant compiled into the artifact being replaced, the artifact cannot replace itself: a stale copy always concludes it is current, and the repair — which lives in the new version — is behind the gate it would open. This is a distinct failure class from "the upgrade broke something", because the observable is a **green no-op**: the user is told they are up to date, and the fleet freezes silently at whatever versions it holds while the publisher's release history looks healthy. It is also self-concealing in the verification dimension the publisher naturally exercises: fresh install works, the artifact on the server is byte-correct, the tag points where it should. Only running the *upgrade* path from a real old install exposes it. The escape hatch survives only because a second delivery channel exists — `curl … | bash` fetches the current installer rather than executing the local one, and was measured to upgrade 2.30.0 → 2.41.0 with the freeze set byte-identical. So the remediation for a shipped instance of this class is a **communication** problem (route the fleet to the channel that bypasses the stale binary), not a code problem: the code fix, however correct, cannot reach the machines that need it.
- **Action**: In any self-updating installer, derive the comparison target from the remote **before** the already-current gate, and fail toward "attempt upgrade" when the probe fails — never toward "nothing to do", since a wrong upgrade is recoverable and a wrong no-op is invisible. Keep a hardcoded version only as a banner/fallback and state in a comment that the gate must not read it. Verify releases by running the upgrade path from a genuine old install, not only fresh install: fresh install cannot exercise the state gate at all. When this class is found already shipped, treat fleet notification via the fetch-then-execute channel as the deliverable; a patch release alone changes nothing for the affected installs.
- **failure_mode**: Naive default: verify a release by installing it into an empty directory, confirming the published artifact's checksum, and checking the tag — then trust that downstream upgrades work because the code path is shared. Why wrong: fresh install never evaluates the "already latest" gate, so a gate that compares a hardcoded constant against itself stays green through every check the publisher runs, while every existing install silently declines to upgrade and reports success.
- **Grounded in**: `.tad/evidence/acceptance-tests/install-smoke-v2410/findings.md` §1 (F1, AC12/AC13 FAIL as honest recording); `.tad/evidence/acceptance-tests/install-smoke-v2410/AC12.txt` (`nothing-to-do=1`, all upgrade anchors 0) vs `AC12b-curl.txt` (all four anchors 1); `tad.sh:1436-1441` + L49-58 + L1509 (the v2.41.0 ordering fix, commit `ac0699f`); `menu-snap/tad.sh:22/961/1014` (the 2.30.0 defect as measured)

### A Version-Staleness Grep Gate Without a Maintained Exclusion Contract Ends Every Release in Override - 2026-09-04
- **Context**: v2.44.0 publish. `release-verify.sh version` (fixed-string OLD grep) exited 1 with 14 survivors on a fully-bumped tree: 4 fixture `expected-version` pins (Gate-4-accepted test semantics), 4 provenance/dated pointers, 4 planning-record lines, 1 CHANGELOG back-ref, 1 dirty-file version line. All correctly left unbumped; 33 identity lines bumped, parity green. Shipped via human-signed scoped exception (Amendment A1, this-release-only).
- **Discovery**: A staleness grep cannot distinguish identity markers from historical references, and every release ADDS historical references (new fixtures pin OLD, new changelog entries cite OLD, new contracts date OLD). Without a maintained exclusion contract, the gate's false-positive count grows monotonically — each release's correct outcome becomes STOP + override, which normalizes gate exceptions.
- **Action**: Maintain the version gate's exclusion set as a first-class artifact (fixture pins, provenance/dated comments, CHANGELOG history bodies, planning narratives). When the gate fires, classify survivors (identity vs historical) before deciding; never "fix" a red gate with history-falsifying edits (bumping a fixture pin or a dated record) — that converts verifier debt into content corruption. If an exception ships, record rationale + sign-off and file the contract update as its own design flow (touching the verifier needs its own Gate).
- **failure_mode**: Naive default A: treat exit 1 as product drift and bump every hit — falsifies fixtures, contracts, history. Naive default B: re-run/waive until green — normalizes overrides. Why wrong: both mistake a stale exclusion contract for a product defect; the fix belongs to the verifier, not the tree.
- **Grounded in**: `COMPLETION-20260904-publish-v2440-STOPPED.md` §3 (14-row classification), `HANDOFF-20260904-publish-v2440-bundle.md` §10 (A1), v2.43.0 precedent (NEXT held OLD only on the version line; pins/provenance are new since v2.43.0)

### Prove Install and Upgrade From the Download-Shaped Source — In-Repo Gates Cannot See Source-Only References or Git-Dependent Cleanup - 2026-10-14
- **Source confidence**: 实测
- **Selector**: Triggers before tagging or publishing a release that changes activation text, routing files, migration manifests or deprecation lists; when a release claims fresh installs or upgrades work; when every in-repo gate is green but no install was made from the exact release bytes. Near-miss exclusion: does NOT trigger for releases whose only change is documentation that no installed project reads.
- **Context**: Two instances in one major release and its patch. (1) Activation instructions told every role to read two knowledge files that exist in the source repository but not in a fresh install. Every in-repo gate passed; a fresh install from `git archive` of the release commit, activated on one harness, answered "Activation is incomplete: the required … files are missing". The fix (an absent knowledge file counts as read and empty) was made before tagging, and both harnesses activated. An earlier phase had already observed that fresh installs lack those files. (2) The release's migration manifest, used for upgrades from the previous major line, was rejected by the migration engine, and, once valid, the engine still deleted nothing: it only acts when it can compare targets with `git show v{old}:{path}` from a git source tree, and download installs use a tarball, so every entry reported "skipped-detection-unavailable". A manifest-validity gate and a fresh install both passed; only a real upgrade from a genuine old install showed the stale files remaining. The patch release moved the cleanup to the deprecation list, which runs without git, and proved it with five real upgrades from four old versions on two harnesses, sourced from `git archive`.
- **Discovery**: The repository is a superset of an install: it has knowledge files, git history and tags that installed projects lack, so any behaviour that depends on those passes in the repo and fails in the field. The download path differs from the developer's path in exactly the ways that matter (no `.git`, no history, no project knowledge), and neither in-repo gates nor fresh installs exercise upgrade-only code.
- **Action**: Before tagging, for each target harness: (a) install from `git archive {release-sha}` (no `.git`) into an empty project and activate each role, reading the reply; (b) install a genuine older release from `git archive v{old}`, upgrade it with `git archive {release-sha}` as the source, and assert the removed/renamed paths and preserved user data by hash. Treat any instruction that names a file as something to test in a project where that file is absent, and say in the instruction what to do when it is absent.
- **failure_mode**: Naive default: run the release gates in the repository, do one fresh install from the working tree, and trust that upgrades share the code path. Why wrong: the working tree has files and git metadata the download lacks, so activation reads and git-dependent migrations succeed there and fail for every user; a fresh install never runs upgrade cleanup at all.
- **Validator**: The release record has, per harness, a fresh-install transcript whose source line is `git archive {release-sha}` and an upgrade record from at least one genuine older version whose stale-path count after the upgrade is 0 and whose user-knowledge hash is unchanged.
- **Grounded in**: `.tad/evidence/yolo/cora-conductor-role/phase4d-install-codex.md` "Before fix"; commit `ad9a8b93`; `phase4d-impl-review-release-r1.md` P2 item 3; `phase2-gate-report.md` candidate 6; `HANDOFF-2026-10-14-cora-conductor-role-phase4f.md` §1.3 finding 1; `phase4e-impl-review-release-r1.md` P1-1; `phase4f-upgrade-{u300,u320,u330,u400}-codex.md`, `phase4f-upgrade-u330-claude.md`; `phase4bd-gate-report.md` KC-2, `phase4ef-gate-report.md` KC-A. Related: `release-sync.md` 2026-08-11 (verify the upgrade path from a genuine old install)

### Cleanup That Runs After the Framework Copy Can Delete or Overwrite What the Copy Just Shipped — Keep Deprecated and Rename-Target Paths Disjoint From Shipped and Generated Paths - 2026-10-14
- **Source confidence**: 实测 (instances 1–2); 推断 (the future-reship hazard in instance 3)
- **Selector**: Triggers when adding or editing a deprecation entry, a migration delete/rename, or any installer step that removes or moves files after the framework copy; when a path once removed is shipped or generated again; when an upgrade log's removal count exceeds the change's own list. Near-miss exclusion: does NOT trigger for cleanup that runs before the copy and only touches paths the release does not ship.
- **Context**: Three instances in one installer. (1) An upgrade on non-default harnesses removed a hooks file through a deprecation key from many versions earlier, then regenerated it unconditionally in the same run; a hand-edited copy survived only in the backup. (2) A migration rename's target was a file the installer had already copied from the new release; whenever the engine could run (git source), `mv` would have overwritten the new file with the old content. The rename was turned into a delete. (3) The patch added a deprecation key at the floor version for three retired paths; that key applies to every future upgrade of any project at or above that version and runs after the copy, so a future release that ships one of those paths again would have it deleted on install. The release's own check covered only that release.
- **Discovery**: The installer's order (copy, then clean) makes every cleanup entry a standing claim that its paths are never shipped or generated again. The claim is invisible: nothing compares the cleanup lists with the shipped tree, and the result looks like a successful install with the wrong file count.
- **Action**: Keep a standing release check that the set of deprecated paths and migration rename sources/targets is disjoint from (a) the shipped tree of the release and (b) every path the installer generates. Never rename onto a path the installer has already copied; delete the old path instead. When a log reports more removals than the change lists, trace each extra path before publishing.
- **failure_mode**: Naive default: add a deprecation or rename entry for the paths retired in this release and test that they disappear. Why wrong: entries are permanent and run after the copy; a later release that ships or generates one of those paths has it removed or overwritten on every upgrade, and the only symptom is a removal count one higher than expected.
- **Validator**: A release gate computes the intersection of all deprecation/migration paths with `git ls-files` of the release tree and with the installer's generated-path list; the intersection is empty or every member is an explicitly documented regenerate-after-delete.
- **Grounded in**: `.tad/deprecation.yaml` (key "2.3.0" lists the hooks file; key "3.0.0"); `.tad/evidence/yolo/cora-conductor-role/phase4f-upgrade-u330-codex.md` and `phase4f-upgrade-u400-codex.md` logs ("Removed 4"); `HANDOFF-2026-10-14-cora-conductor-role-phase4f.md` §1.3 finding 2; `phase4ef-gate-report.md` G4-4, KC-A, KC-C
